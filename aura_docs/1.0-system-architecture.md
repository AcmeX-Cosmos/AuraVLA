# AuraVLA System Architecture

## 1. Scope

AuraVLA is a ROS 2 and Isaac Sim based vision-language-action system for
robotic pick-and-place tasks. It converts a natural-language instruction such
as `把香蕉放进篮子里` into a validated high-level task, estimates a physical
grasp pose from RGB-D perception, plans a collision-aware motion, executes the
motion in Isaac Sim, and verifies the physical result.

The system is deliberately split into semantic reasoning, geometric
perception, motion planning, physics execution, and result verification. The
NVIDIA VLM does not generate joint commands or low-level trajectories.

## 2. End-to-End Data Flow

```text
User instruction and scene image
              |
              v
Interactive NVIDIA Agent
  Nemotron VLM + JSON Schema validation
              |
              v
High-level task plan
  pick / place / move_to
              |
              v
ROS 2 orchestration and execution bridge
              |
              v
Isaac Sim RGB-D camera
              |
              v
SAM target mask + selected grasp backend
  AnyGrasp <--------------------> GraspNet
              |
              v
Calibrated world-frame grasp pose
  temporal weighted fusion and outlier rejection
              |
              v
Lula IK/RRT or MoveIt 2 plan-only backend
              |
              v
Isaac Sim PhysX execution
  arm motion + physical gripper contact
              |
              v
Lift / transport / placement verification
              |
              +---- failure ----> bounded replan or explicit failure
```

## 3. Software Layers

### 3.1 Semantic interaction layer

The interactive NVIDIA Agent is a separate process so it can own terminal
input and NVIDIA API communication without blocking the ROS 2 launch system.
It sends the current image and user instruction to the NVIDIA Nemotron VLM.

The VLM output is restricted to semantic task data. The schema validator
rejects malformed output, scalar target fields where lists are required, and
low-level motion commands such as `joint_move` or `cartesian_move`.

Main modules:

- `aura_perception/aura_perception/nvidia_agent.py`
- `aura_perception/aura_perception/vlm_client.py`
- `aura_planning/aura_planning/schemas.py`
- `aura_planning/aura_planning/task_planner.py`

### 3.2 ROS 2 middleware layer

ROS 2 Humble provides process-level communication and lifecycle separation:

- `aura_perception`: semantic perception and doability evaluation
- `aura_planning`: high-level task plan generation and validation
- `aura_execution`: execution action server and Isaac task bridge
- `aura_verification`: completion and geometric result checking
- `aura_orchestration`: task lifecycle coordination and bounded replanning
- `aura_isaac_bridge`: Isaac status and transport telemetry publication

The complete graph is started by
`aura_bringup/launch/aura_bringup.launch.py`. The interactive NVIDIA Agent is
started separately by `aura_scripts/start_nvidia_agent.sh`.

### 3.3 Isaac runtime and file bridge

Isaac Sim is expected to be open with the VS Code Edition executor enabled.
The runtime injection script loads the AuraVLA robot code into that process.

The cross-process task protocol uses JSON files under
`/tmp/aura-vla-control`. This keeps the Isaac runtime boundary independent of
the ROS 2 Python process while allowing ROS nodes to monitor status and
transport events. The file bridge includes status polling, heartbeats, request
timeouts, and stale-runtime handling.

## 4. Grasp Perception

### 4.1 Common perception pipeline

Both grasp backends use the same surrounding pipeline:

1. Capture a fresh RGB-D frame from the Isaac Sim camera.
2. Project the target Prim center into the image.
3. Generate a SAM target mask.
4. Run the selected grasp detector on the masked point cloud.
5. Convert the detector pose into the robot world frame.
6. Apply backend-specific calibration when configured.
7. Fuse a short sequence of observations using score, depth quality, and geometric validity.
8. Reject temporal outliers, excessive dispersion, and low-confidence results.

The shared implementation is in
`aura_hardware/aura_isaac_bridge/core/perception.py` and
`aura_hardware/aura_isaac_bridge/core/grasp_fusion.py`.

### 4.2 Backend selection

The selected backend is controlled by `aura_bringup/config/config.yaml`:

```yaml
perception:
  grasp_backend: "graspnet"
```

Supported values are:

- `anygrasp`: licensed AnyGrasp SDK and `checkpoint_detection.tar`
- `graspnet`: GraspNet baseline and `checkpoint-rs.tar`

The unified dispatcher is `infer_grasp_fused_world_pose(...)`. The individual
interfaces remain available as:

- `infer_anygrasp_fused_world_pose(...)`
- `infer_graspnet_fused_world_pose(...)`

Only the selected backend is loaded for a request. Each backend keeps its own
model cache so a long-lived Isaac process does not repeatedly load the model.
The two backends must not share incompatible `pointnet2`, `gsnet`, or
MinkowskiEngine module state.

### 4.3 Failure semantics

Perception is fail-closed. If the selected detector, dependency, checkpoint,
license, mask, or temporal fusion gate is unavailable, the task returns an
explicit error such as `ANYGRASP_UNAVAILABLE` or `GRASPNET_UNAVAILABLE`.
The execution layer does not replace a missing detector result with a USD
geometric center.

## 5. Motion Planning and Physical Execution

The task executor is shared by both perception backends. It performs:

- top-down and constrained grasp orientation selection
- reachability checks for the complete grasp and lift pose
- Lula IK warm starts and collision-aware RRT planning
- optional MoveIt 2 plan-only requests through the JSON bridge
- minimum-jerk trajectory interpolation
- bounded joint-step and frame-rate constraints
- tabletop, basket, finger, and payload collision checks
- segmented carry-path replanning while the gripper remains closed

MoveIt 2 is integrated as a planning backend with SRDF, kinematics, joint
limits, OMPL, and planning-scene configuration under `aura_moveit_config/`.
Isaac Sim remains the trajectory executor. When MoveIt 2 is unavailable, the
configured Lula fallback can be used:

```yaml
planner:
  backend: "moveit"
  fallback_to_lula: true
```

The physical gripper is controlled through Isaac Sim articulation joints. A
successful grasp requires real finger contact, contact force or preload
feedback, object displacement during lift, and stable containment during
transport. FixedJoint attachment and other simulated object binding shortcuts
are not part of the execution design.

## 6. Closed-Loop Verification

Verification is performed after each important phase rather than only after
the final release:

- hover pose reached
- grasp pose reached
- physical finger alignment and contact confirmed
- object lifted above the table
- payload remains within the expected transport envelope
- basket approach and placement corridor remain collision-free
- object is inside the basket after release

During transport, the runtime compares a fresh detector observation with the
expected object position derived from the gripper motion. A deviation above
the configured threshold requests a bounded replan. Replanning cannot bypass
contact, lift, or placement verification.

## 7. ROS 2 Telemetry and Foxglove

The Isaac bridge republishes JSON transport events and standard ROS messages
for plotting. Relevant topics include:

```text
/aura/transport_tracking
/aura/anygrasp/state
/aura/anygrasp/confidence
/aura/anygrasp/position_error_m
/aura/anygrasp/observed_position
/aura/anygrasp/expected_position
/aura/anygrasp/position_error_vector_m
```

The historical `/aura/anygrasp` topic prefix is retained for Foxglove
compatibility even when `grasp_backend` is set to `graspnet`; the payload
contains the active backend and event type.

Foxglove connects to the WebSocket bridge at `ws://localhost:8765` when the
bringup launch starts it.

## 8. Configuration and Startup

The primary runtime configuration is
`aura_bringup/config/config.yaml`. It controls NVIDIA API settings, the grasp
backend, detector paths, calibration, fusion thresholds, planner backend,
robot parameters, camera settings, and telemetry.

Typical startup:

```bash
cd /home/acmex/Code/learning/courses/AuraVLA
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 launch aura_bringup aura_bringup.launch.py
```

In another terminal:

```bash
cd /home/acmex/Code/learning/courses/AuraVLA
source /opt/ros/humble/setup.bash
source install/setup.bash
./aura_scripts/start_nvidia_agent.sh
```

To select a backend for one runtime process:

```bash
AURA_GRASP_BACKEND=anygrasp ./aura_scripts/start_isaac_robot.sh
AURA_GRASP_BACKEND=graspnet ./aura_scripts/start_isaac_robot.sh
```

Environment variables take precedence over the YAML value. Restart or reload
the Isaac runtime after changing the backend because the detector configuration
is imported during runtime initialization.

## 9. Runtime Dependencies and Boundaries

- Ubuntu 22.04
- ROS 2 Humble
- Isaac Sim Python runtime
- Python 3.10+ for ROS-side packages
- Python 3.11 ABI for the current Isaac Sim runtime and compiled grasp extensions
- NVIDIA Nemotron API credentials for VLM inference
- SAM model weights for target segmentation
- AnyGrasp SDK, matching checkpoint, and machine license when using AnyGrasp
- GraspNet baseline, matching PointNet++ CUDA extension, and checkpoint when using GraspNet
- MoveIt 2 installation only when the MoveIt planning backend is enabled

Private SDK files, checkpoints, API keys, and AnyGrasp license files must stay
outside version control. The repository configuration should contain paths or
environment-variable references, not private credentials or license material.
